# Blueprint: likec4-discover (Portable Code-to-LikeC4 Skill)

## Goal upfront

Build a standalone, portable Agent Skill that scans a repo (TypeScript/JavaScript or Python first, single-language repos supported — only the matching runtime is required) and generates a valid LikeC4 model (`specification` + `model` + `views`). It runs unchanged in OpenCode, Antigravity, Claude Code, Cursor, and Codex.

Core rule: scripts do deterministic work, LLM does only titles, grouping confirmation, and proposal promotion. No LLM ever writes DSL syntax directly.

This replaces the old `code2c4` / `generate_likec4_model` MCP-wrapper idea.

---

## 1. Why a standalone skill (not an MCP server)

- Agent Skills open spec (`agentskills.io`) is the portable core: `name` + `description` + Markdown body + `scripts/`, `references/`, `assets/`. All major agents read it.
- Neutral home is `.agents/skills/likec4-discover/` (Antigravity, Cursor, Copilot, VS Code, Codex, OpenCode all read it). Copying the same folder to `.claude/skills/` covers Claude Code.
- No client extensions (`allowed-tools`, `model`, hooks) — they are ignored outside Claude Code.
- No bundled LLM keys. The host agent (OpenCode, Claude, etc.) provides the LLM.

## 2. Relation to LikeC4 ecosystem

LikeC4 already ships (v1.59.x, July 2026):

- Official Skill `likec4-dsl` (`npx skills add https://likec4.dev/`) — full DSL reference. We reference it, never duplicate it.
- Official MCP read-path `@likec4/mcp` / `likec4 mcp` (`search-element`, `query-graph`, `preview-view`, etc.). We complement it, never duplicate it.
- Programmatic API: `LikeC4.fromSource().getErrors()` (via `emit.mjs --check`, optional) -> CLI `likec4 validate` -> `computedModel().elementsWhere()` vitest checks.

Our skill is write-path only: `scan repo -> IR -> .c4`. Tracked upstream in discussion likec4/likec4#3239. Long-term goal is a `Tooling > Community` docs listing (like Erode/AspireC4), not a core merge.

Erode (drift detection) is explicitly deferred to Phase 3 consideration only.

## 3. Deterministic pipeline

```
scan.mjs + scan.py -> IR JSON (elements + proposals) -> deterministic grouping (dir-tree + fan-in/out) -> host LLM titles/confirm/promote -> emit.mjs -> spec.c4/model.c4/views.c4 -> validate
```

- `specification { }` is mandatory. Default kinds: `person, system, container, component, database` (styled per P2d), relationships `http, kafka, s3, promql, inproc` (+ legacy `calls, imports, inherits` aliases), no `tag autogenerated` (provenance = file header). Fixed sets — LLM never invents kinds.
- `views { }` auto-generated: `view index { include * }` + one `view of <system> { include * }` per top-level system.
- `deployment { }` and dynamic/sequence views are out of scope for v1.
- Every generated element keeps `tags: ["autogenerated"]` in IR (metadata only, never rendered). Provenance in output is a file header comment (`// Generated by likec4-discover ...`), not per-element tags (badge spam). Editing replaces, never merges silently (`toBuilder(editable)` semantics).

## 4. IR contract (replaces old boundaries JSON)

Old `{ boundaries: { api_layer: { components: [...] } } }` is dropped: bare names collide, no file info, no import-vs-call distinction.

Envelope: `{ "elements": [...], "proposals": [...] }`. Per-element record (child shown; file parents omit `symbol`/`parent`):

```json
{
  "fqn": "demo.serving.app.predict",
  "kind": "component",
  "title": "Predict",
  "file": "serving/app.py",
  "lang": "py",
  "symbol": "predict",
  "line": 212,
  "parent": "serving/app.py",
  "route": "POST /predict",
  "imports": [],
  "calls": [{ "to": "demo.serving.app.decode_image", "kind": "inproc" }],
  "extends": [],
  "technology": "FastAPI",
  "tags": ["autogenerated"]
}
```

Optional element fields: `symbol` (class/function/route name), `line` (1-based evidence line), `parent` (scanner: parent file path; labeled IR: parent FQN also accepted), `route` (e.g. `POST /predict`, rendered as `description`). Per-proposal record (infra/actor candidates, never auto-added):

```json
{ "kind": "container", "title": "Kafka Message Broker", "technology": "Apache Kafka", "source": "manifests/09-kafka.yaml", "reason": "k8s Deployment kafka" }
```

Rules:

- Identifiers: `[A-Za-z_][A-Za-z0-9_-]*` only, no dots, not starting with digit. Dots separate FQN levels only.
- FQN must be unique project-wide. Cross-file refs always use full FQN.
- Granularity (default, P2a): file = container-ish parent; module classes, top-level functions, and route handlers (FastAPI decorators / Express-style registrations) = nested components with `parent` + `line` evidence. Symbol-free files fall back to file = component.
- Infra/actor discovery (P2b): deterministic `proposals` from k8s manifests (`kind`/`metadata.name`/`image` via line-regex, no YAML dep), prometheus scrape jobs, client-lib signals (`aiokafka`→kafka, `mlflow`→mlflow, `prometheus_client`→prometheus, ...), and a `person/Client` proposal whenever route symbols exist. LLM promotes/drops each proposal at labeling time.
- Relationship typing (P2c): intra-repo import → `imports`; same-file call → `inproc`; kafka/mlflow/s3/prometheus client usage → `kafka`/`http`/`s3`/`promql` with `// evidence: file:line` comments. LLM confirms labels.
- Default hierarchy = directory tree + fan-in/fan-out counts. LLM labels/confirms, never structures from scratch.
- No direct parent-child `->` relationships.
- Cap output (~200 elements default, symbols included). Ignore `node_modules, dist, build, .venv, __pycache__, .git` + symlinks + respect `.gitignore`. `--include` replaces defaults, `--exclude` merges with defaults. `includeTests: false` default. Test basenames (`test_*.py`, `*_test.py`, `*.test.*`, `__tests__`, `/tests?/`) excluded unless `--include-tests`.

## 5. Skill layout (Agent Skills spec)

```
likec4-discover/  (repo `likec4-discover`)
  skills/likec4-discover/   # shippable skill (SKILL.md <350 lines, scripts/, references/, assets/)
  fixtures/                 # tiny-ts, tiny-py, tiny-api, tiny-tsconfig
  test/                     # node:test + python unittest (stdlib only)
  scripts/                  # check-skill.mjs, validate-fixtures.sh (dev harness)
  .github/workflows/ci.yml  # npm test + check:skill + fixtures
  docs/plan.md, README.md, LICENSE
```

`SKILL.md` frontmatter:

```yaml
---
name: likec4-discover
description: Scan TypeScript/Python repo to IR and generate validated LikeC4 model (specification+model+views). Use when user asks for architecture diagram, C4 model, likec4, code-to-diagram, or codebase overview.
license: MIT
compatibility: Requires node >=20 (TypeScript/JavaScript repos) and/or python3 (Python repos)
metadata:
  version: "0.1.0"
---
```

Body sections: Goal -> 5-step workflow (scan -> group/label -> emit -> validate -> preview/serve) -> FQN guardrails -> Constraints (never hand-write DSL, never invent kinds, ask before exceeding budgets).

## 6. Scripts (zero-dependency core + optional enhancement)

- Core runtime: `node >=20` and/or `python3` (per target language — single-language repos need only their runtime; `scan.mjs` skips the `scan.py` spawn when no `.py` files exist). No `npm i`, no `ts-morph`, no `oxc-parser` (serde overhead + extra dep rejected for v1 portability).
- `scan.mjs`: recursive walk with `include/excludeGlobs`, `maxFiles`; TS/JS extraction (imports via regex, exported classes/functions + Express-style and NestJS-decorator routes as symbols with lines); tsconfig `paths` alias resolution (no external parser); single spawn of `scan.py --root <dir>` (forwards `--exclude`/`--include-tests`, skipped when no `.py` files); merges to IR JSON to stdout/file.
- `scan.py`: one invocation, walks `.py` files, uses `ast` module (classes, functions, FastAPI route decorators with paths + linenos, same-file call edges → `inproc`), resolves relative imports, `--exclude` support, prints JSON, exits non-zero with clear error on syntax failure.
- `scan.infra` (inside `scan.mjs`, stdlib only): k8s manifests + prometheus configs + client-lib signals → `proposals[]` with `source` evidence.
- `emit.mjs`: string-template canonical (no likec4 dep, portable); optional `--check` runs `LikeC4.fromSource().getErrors()` when the `likec4` package is installed (dynamic import, skipped with a note otherwise; fail-closed on errors). Nests `parent` children as sub-components, renders typed relationships with labels, emits `// evidence:` comments. Fails closed on duplicate FQN or bad identifier. FQN assignment structural (`<system>.<area>.<file>[.<symbol>]`, filename-based leaves — titles are display-only) with sanitize + dedupe.
- `likec4` CLI is required in CI: `likec4 validate` must report zero errors. Locally it is progressive enhancement: if absent, template self-check only. `preview-view` MCP tool for iterate-without-files.

## 7. Validation strategy

1. `emit.mjs` throws on duplicate FQN / bad identifier at generation time.
2. CI requires `likec4`: `LikeC4.fromSource().getErrors()` must be empty; `likec4 validate` must report zero errors; `computedModel().elementsWhere()` vitest checks per `guides/validate-your-model`.
3. Fixture repos (tiny-TS + tiny-Python + multi-component FastAPI-style + k8s-manifests) assert the above in CI, including typed rels and evidence lines.
4. Lossy round-trip (`toDSL`/`writeDSL`) is one-way generation, never treated as formatter.

## 8. CodeWiki usage (patterns only, no runtime dep)

CodeWiki is LLM-heavy (requires provider keys or subscription, multi-agent clustering, Python 3.12+). Do NOT depend on `codewiki generate`.

Borrow deterministically:

- `--include` replaces defaults / `--exclude` merges + `.gitignore` respect.
- `module_tree.json` dir-tree grouping default.
- Budgets (`max-tokens-per-module`, `max-depth`) + incremental `--update --compare-to <sha>` (Phase 3).
- Skill UX reference: `skills/codewiki-wiki-generator/SKILL.md` via raw URL.

## 9. Distribution

- Source repo `likec4-discover` (public): skill ships at `skills/likec4-discover/` for `npx skills add <repo>` discovery; root holds dev harness (fixtures, tests, CI) + `docs/plan.md` (internal blueprint, not packed).
- Install: copy `skills/likec4-discover/` to `.agents/skills/` (Antigravity/Cursor/Codex/OpenCode/Copilot) or `.claude/skills/` (Claude Code), or `npx skills add <repo>`.
- Test matrix: automated local checks via `npm run check:skill` (frontmatter, layout, budgets, executability, trigger keywords — green in CI). Manual per host: OpenCode `skill`-tool load, Antigravity skill list, Claude/Cursor trigger phrase "generate likec4 model for ./src", `npx skills add <repo>` (needs published repo).

## 10. Phases

- Phase 1: Scaffold skill files above + 2 fixture repos + CI validate check. (Done.)
- Phase 2a (P2a): Sub-file symbol extraction default (`scan.py` AST classes/functions/routes + `scan.mjs` exports/routes, `parent`/`line` IR fields, nested emit).
- Phase 2b (P2b): Infra + actor `proposals` (manifests/prometheus/client-lib signals, LLM promotes/drops).
- Phase 2c (P2c): Typed relationships (`http, kafka, s3, promql, inproc`) + evidence `link`s.
- Phase 2d (P2d): Richer default spec (person/database shapes, colors, notations) + extended fixtures + CI. (Done.)
- Phase 2e (P2e): `emit.mjs --check` (optional `LikeC4.fromSource().getErrors()`, dynamic import, skip-when-absent) + scoped scan hardening (tsconfig `paths`, NestJS decorators, actor-from-routes proposal) + `tiny-tsconfig` fixture. (Done.)
- Phase 2f (P2f): Source optimization (line-offset tables, single-walk call maps, parent-set, path normalization) + packaging (`skills/likec4-discover/` layout, root README, hygiene) for repo publication.
- Phase 3: Publish repo → upstream follow-up on likec4/likec4#3239 (Community docs PR) → scoped `deployment {}` skeleton (manifest-derived namespaces/instances, human-confirmed env layer) → `--update` incremental mode only after observed regeneration pain.
- Explicitly deferred/hold: dynamic views (needs trace/DAG grounding; static order risks fiction), MCP wrapper (rejected — scripts-behind-skill obsoletes it; `@likec4/mcp` owns read-path), other languages, namespace-package edge cases, broader framework coverage.
